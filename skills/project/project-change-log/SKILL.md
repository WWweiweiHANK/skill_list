# 项目开发变更记录

让后续维护者知道改了什么、为什么改、改在哪里，以及如何验证和撤回。以本次实际文件变动为事实来源，不把计划写成完成。

## 定位同一份记录

先检查用户指定的当前项目目录、AGENTS.md 和既有记录约定。优先续写已有 CHANGELOG.md、变更记录.md 或既定开发日志；不要因为文件名不同创建平行日志。
没有现成记录时，在当前项目根目录创建 CHANGELOG.md。多项目工作区应使用本次实际修改的项目目录，避免写到工具目录。
保留历史内容和原格式，按既有排序添加本次条目。不要为补充一次遗漏而重写整个历史。

## 每次实际修改后的收尾

1. 保存已修改的代码、配置、资源和文档。利用差异或本次操作清单核对自己的改动，避免把用户此前未提交的修改算作本次成果。
2. 在同一条记录中写明日期、任务目的、实际行为变化、关键相对路径、验证结果和已知未完成项。
3. 涉及迁移、配置或持久化数据时，补充维护前提与可行的回退办法；不适用时省略。不要给出会覆盖用户未保存工作的回退命令。
4. 现有策划案或 SPEC 与本次已确认实现冲突时，同步相关段落；尚未确认的设计保持待定。历史日志保留事实，不充当当前规则文档。
5. 检查条目与真实差异一致。只有确实执行成功的验证才能写“通过”；没有运行测试就写“未运行”及原因。

任务中途失败但已有文件变化，也记录完成部分和阻塞。写入失败时在回复中说明，不能声称已保存。
保存文件和维护日志不等于获得发布、部署或远程上传授权；已有明确授权时继续完成，不重复确认。没有远程保存动作时，不声称已上传或云端备份。

## 最小条目参考

沿用现有记录格式；新建时可使用：

```markdown
## 日期 — 任务名称
- 目的：为什么修改。
- 变化：本次已实现的行为变化。
- 文件：关键相对路径及用途。
- 验证：实际执行的检查、结果或未执行原因。
- 待办／维护：仅记录实际遗留事项和适用的回退说明。
```

最终回复简要说明改动、验证及记录位置。Skill 必须在当前工具中被加载才能指导执行；不要承诺未加载时也会自动运行。
